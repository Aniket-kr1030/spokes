## Validation: Python support against a real codebase

v1.1.0's Python support had only ever been exercised against the `f11-python` fixture and a
synthetic scratch project. Run here against a real FastAPI backend (71 `.py` files, `src/kalvi/`
src-layout package, SQLAlchemy + Alembic):

| Signal | Result |
|---|---|
| Nodes / edges resolved | 43 nodes, 73 edges |
| E-RESOLVE warnings | **0** — every relative import resolved |
| Rules fired (with realistic roles applied) | S001 × 11, S002 × 2, S004 × 22, S003 × 0 |
| `explain` on a real module | correct: 18 incoming edges, 17 exports, role, per-rule status |
| `graph` | renders — 43 nodes, 12 directory clusters, no Mermaid syntax error |

Specifics worth recording:

- Multi-level relative imports (`from ..auth.dependencies import get_current_teacher`) resolved
  correctly across sibling packages — the `from X import name` submodule-vs-symbol fallback did
  the right thing on real code, not just the fixture.
- Line/column attribution was accurate on real files (verified against the sources).
- R1's help text correctly emitted the Python `# @spokes hub` pragma, not the TS `//` form.
- Zero unresolved imports across 73 edges is the strongest signal here: it means the filesystem
  resolver's `<mod>.py` → `<pkg>/__init__.py` ordering and the repoRoot/`src` search roots match
  how a real src-layout Python project is actually laid out.

**No new defects found.** No code changes resulted from this run.

The target repo's own `spokes.config.json` was temporarily modified to apply roles for the rule
exercise and restored byte-for-byte afterwards; its working tree was left clean.
