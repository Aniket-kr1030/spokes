# spokes v1.0.0 (M0–M2) Implementation Plan

## Overview

`spokes` is a new CLI tool that parses the static TS/JS import graph of a repository, classifies every file as a **hub** (in-degree ≤ 1) or **spoke** (out-degree ≤ 1), enforces those degree rules plus acyclicity, and mechanically renders the result as a Mermaid/DOT architecture diagram. This plan covers a from-scratch build of milestones M0 (skeleton), M1 (checker), and M2 (visuals + suggest) — the shippable v1 per the PRD. M3 (write-mode, watch mode, incremental cycle checking, non-TS adapters, LSP) is explicitly out of scope.

## Problem Statement

There is no existing codebase — this is a greenfield project (empty directory, git just initialized, no `docs/ARCHI.md` yet). This plan doubles as the initial architecture: it must produce a `src/` layout that itself obeys the hub/spoke rules, since the acceptance criteria require `spokes check` to pass with 0 errors on its own source (the "meta" fixture in PRD §11).

## Solution Architecture

Everything flows one direction, entry → hubs → spokes → leaf types, which is what makes the tool's own source acyclic and degree-compliant by construction:

```
cli.ts (hub, in=0)
 ├─ init.ts        (hub, in=1 ← cli.ts)
 ├─ graph-builder.ts (hub, in=1 ← cli.ts)   -- builds the Graph ONCE
 ├─ check.ts       (hub, in=1 ← cli.ts)     -- receives Graph as a fn argument
 ├─ graph.ts       (hub, in=1 ← cli.ts)     -- receives Graph as a fn argument
 ├─ suggest.ts     (hub, in=1 ← cli.ts)     -- receives Graph as a fn argument
 └─ explain.ts     (hub, in=1 ← cli.ts)     -- receives Graph as a fn argument
```

`graph-builder.ts` lives at the **top level of `src/`** (`src/graph-builder.ts`, a sibling of `cli.ts`/`check.ts`/etc., not under `src/core/`) so it lands in the `src/*.ts` → hub roles glob alongside the other command modules — everything actually under `src/core/**` is a spoke. This placement is load-bearing for the meta-dogfooding test (§17): a hub needs unconstrained out-degree, and `src/core/**`'s default role in this repo's own config is spoke.

The key architectural trick: `graph-builder.ts` builds the `Graph` object exactly once inside `cli.ts`, which then **passes it as a plain function argument** to `check`/`graph`/`suggest`/`explain`. Passing data as a call argument is not a static import, so it creates no edge — this is what lets four different command modules all consume the same graph without any of them (or `graph-builder.ts`) violating the in-degree-≤1 hub rule.

Below `graph-builder.ts` everything is a **spoke** with out-degree ≤ 1, importing only `types.ts` (which itself has out-degree 0, so it can never be part of a cycle):

```
parser.ts    → types.ts   (spoke)
resolver.ts  → types.ts   (spoke)
roles.ts     → types.ts   (spoke)
config.ts    → types.ts   (spoke)
rules/r1..r4 → types.ts   (spoke each; in-degree unconstrained, so check.ts + suggest.ts can both import r3)
render/*.ts  → types.ts   (spoke each; in-degree unconstrained, so check/graph/explain/suggest can share them)
types.ts     → (nothing)  (leaf spoke, out-degree 0, in-degree unconstrained)
```

`graph-builder.ts` itself is a hub (in-degree 1, only `cli.ts` calls it), so its own out-degree is unconstrained and it is free to import `core/parser.ts`, `core/resolver.ts`, `core/roles.ts`, and `types.ts` directly. It does not import `core/config.ts` — the already-loaded `SpokesConfig` is passed in as a function argument by `cli.ts`, so there is no need for `graph-builder.ts` to load config itself.

Test files (`**/*.test.*`) are excluded from the linter's own `include` glob by default config, so `tests/` is exempt from the hub/spoke rules and can import freely.

### 2. `src/types.ts` (leaf spoke)

Shared type definitions used everywhere: `Role = 'hub' | 'spoke' | 'unmarked'`, `Loc = {file, line, col}`, `Node = {path, role, exports: string[]}`, `Edge = {from, to, locations: Loc[]}`, `Graph = {nodes: Map<string, Node>, edges: Edge[]}`, `Diagnostic = {code, message, primary: Loc, related: Loc[], severity: 'error'|'warning'}`, `SpokesConfig` (mirrors §5 schema), `CheckResult = {version: 1, errors: Diagnostic[], warnings: Diagnostic[], stats: {...}}`. Zero internal imports — this is what keeps the whole graph acyclic.

`types.ts` lives at the same top level as `cli.ts`/`graph-builder.ts`/etc., so it would also match a literal `src/*.ts → hub` roles glob — but it must stay a spoke (in-degree ~20, from every other module importing it, which would trip R2 if misclassified as a hub). It carries a `// @spokes spoke` file pragma (first 5 lines) to force this — pragma wins over config glob per §4 — rather than relying on roles-array ordering.

### 3. `src/core/config.ts` (spoke, → types.ts)

- Loads `spokes.config.json` from repo root (same dir as `package.json`, found via upward search from CWD).
- Hand-rolled structural validation against the known shape (required keys, enum values for `defaultRole`/`strictCycles`/`singleExport`/`typeOnlyEdges`/`externalPackages`, array-of-glob-objects for `roles`). On failure, print the failing key path and exit 2, matching §5's "print the schema path of the failure" requirement.
- Applies defaults for any omitted keys (the full default object from §5).
- Exports exactly one function, satisfying R4: `loadConfig(cwd: string): SpokesConfig`.

### 4. `src/core/roles.ts` (spoke, → types.ts)

Exports exactly one function, `resolveRole(fileContents, relPath, config): Role`, satisfying R4. Internally (not exported) it composes two private helpers:

- `resolvePragma(fileContents: string): Role | undefined` — scans first 5 lines against the case-insensitive regex from §4.
- `resolveConfigRole(relPath: string, config: SpokesConfig): Role | undefined` — first-match-wins walk of `config.roles`, using a small hand-rolled glob-to-regex matcher (no extra runtime dep — this is the one place a naive glob engine is written, kept intentionally minimal: `**`, `*`, `{a,b,c}` brace groups only, matching the patterns actually used in the PRD's examples and fixtures).
- `resolveRole` combines them: pragma wins, else config glob, else `config.defaultRole`.

### 5. `src/core/parser.ts` (spoke, → types.ts; external dep: `typescript`)

Exports exactly one function, satisfying R4: `parseFile(absPath: string): {specifiers: ImportSpecifier[], exports: string[]}`, where `ImportSpecifier = {text: string, loc: Loc, typeOnly: boolean}` is a non-exported local type (internal to `parser.ts`, not re-exported).
- Uses `ts.createSourceFile` with `scriptKind` selected from the file extension, then a manual `ts.forEachChild` walk (per §6, no `ts-morph`, no regex parsing) to collect:
  - `ImportDeclaration` (`import ... from '<literal>'`), tracking `isTypeOnly` on the import clause and on individual named specifiers (`import { type X }`).
  - `ExportDeclaration` with a `moduleSpecifier` (`export ... from '<literal>'`).
  - `CallExpression` where the callee is `import` (dynamic import) or the identifier `require`, and the sole argument is a `StringLiteral`.
  - Top-level `export` names (`export default`, `export const/function/class`, named export lists, `export type`) for the exports list used by R4 and `explain`.

### 6. `src/core/resolver.ts` (spoke, → types.ts; external dep: `typescript`)

Exports exactly one function, satisfying R4: `resolveSpecifier(repoRoot: string, fromAbsPath: string, specifierText: string): {kind: 'relative'|'bare'|'unresolved', absPath?: string}`. Internally (not exported) it maintains a module-level `Map<repoRoot, ResolutionContext>` cache — the first call for a given `repoRoot` builds and caches the context (reads `tsconfig.json` once via `ts.readConfigFile` + `ts.parseJsonConfigFileContent`, capturing `paths`/`baseUrl`; builds a reusable `ts.CompilerOptions` + a minimal `ts.ModuleResolutionHost` backed by `ts.sys`), subsequent calls for the same `repoRoot` reuse it. This preserves the "parse tsconfig once, not per file" requirement for the ≤2s/1000-files performance target while keeping the public surface to one export.
- `resolveSpecifier` delegates to `ts.resolveModuleName(specifierText, fromAbsPath, compilerOptions, host)` using the cached context. Bare specifiers (npm/node builtins, or anything `ts.resolveModuleName` resolves into `node_modules`) map to `'bare'` (no edge, per `externalPackages: "ignore"`). Relative specifiers that fail to resolve map to `'unresolved'` (triggers `E-RESOLVE` warning, no edge). The manual extension-order fallback in §6 is used only if `ts.resolveModuleName` doesn't already resolve it (it normally does, given correct compiler options) — implemented as a thin fallback pass, not hand-rolled alias logic.

### 7. `src/graph-builder.ts` (hub, in-degree 1 ← cli.ts only; → core/parser.ts, core/resolver.ts, core/roles.ts, types.ts; external dep: `fast-glob`)

Placed at `src/graph-builder.ts` (top level, not `src/core/`) so the repo's own `roles` config (§17) classifies it as a hub via the `src/*.ts` glob — it needs unconstrained out-degree for the four internal imports below, which a `src/core/**` → spoke classification would forbid.

- Exports exactly one function, satisfying R4: `buildGraph(config: SpokesConfig, repoRoot: string): {graph: Graph, resolveWarnings: Diagnostic[]}`.
- Uses `fast-glob` with `config.include`/`config.exclude` to enumerate files.
- For each file: reads contents once, calls `parser.parseFile`, resolves each specifier via `resolver.resolveSpecifier` (skipping edges for `typeOnly` specifiers when `config.typeOnlyEdges === "ignore"`), determines role via `roles.resolveRole`, and accumulates into `nodes`/`edges`, deduplicating multiple A→B imports into one `Edge` with a merged `locations` array.
- Emits an `E-RESOLVE` warning `Diagnostic` for each `'unresolved'` relative specifier.
- Nodes and edges are stored keyed by absolute path but the builder guarantees stable insertion order isn't relied upon — all consumers (rules, render) sort lexicographically themselves (determinism requirement lives at the render/rule layer, not the builder).

### 8. `src/rules/r1-spoke-outdegree.ts`, `r2-hub-indegree.ts`, `r3-acyclicity.ts`, `r4-single-export.ts` (each a spoke, → types.ts only)

- R1, R2, and R4 each export a single pure function `check(graph: Graph, config: SpokesConfig): Diagnostic[]`, satisfying R4's own single-export rule for each of these spoke modules.
- **R1**: group edges by `from`, filter nodes with `role === 'spoke'` and out-degree > 1, emit `S001` with the exact multi-line template from §7 (one `edge N →` line per outgoing edge, sorted by target path).
- **R2**: group edges by `to`, filter nodes with `role === 'hub'` and in-degree > 1, emit `S002` with one `caller N:` line per incoming edge, sorted by caller path.
- **R3** (`r3-acyclicity.ts`) exports exactly one function instead of the `check` pattern, to stay at one export: `analyzeCycles(graph: Graph, config: SpokesConfig): {diagnostics: Diagnostic[], cycles: Cycle[]}`. Internally: iterative three-color DFS (explicit stack, not recursive, to avoid stack-depth limits on large repos) over all nodes when `config.strictCycles` is true (else only marked nodes). On a back-edge, reconstruct the cycle from the DFS stack, normalize/dedupe by the sorted set of member paths. `cycles` is the raw deduped cycle list; `diagnostics` is one `S003` per distinct cycle using the exact template (cycle path + closing edge location), derived from `cycles`. `check.ts` uses `.diagnostics`; `suggest.ts` and `explain.ts` use `.cycles` — this is why both importing `r3-acyclicity.ts` is legal: `r3` is a spoke with unconstrained in-degree, and callers just destructure the one exported function's return value differently.
- **R4**: for nodes with `role` in `{hub, spoke}`, count exports (excluding `export type` names when `typeOnlyEdges === "ignore"`); if count > 1, emit `S004` at the level from `config.singleExport` (`off` skips entirely). **A count of 0 does not trigger S004** — a module with no non-type-only exports (e.g. a pure type-definitions file) presents no barrel-file fan-out risk, which is what R4 exists to discourage; there is no per-file R4 override in the config schema, so this interpretation is what lets `types.ts` (§2, zero value exports) pass R4 as a spoke without a separate exemption mechanism. This is a documented reading of the PRD's "should export exactly one symbol" wording, since the PRD's own S004 example is anchored to over-fan-out, not to files with nothing to export.

### 9. `src/render/text.ts`, `json.ts`, `mermaid.ts`, `dot.ts`, `html.ts`, `diff.ts` (each a spoke, → types.ts only; each exports exactly one function, satisfying R4)

- `text.ts`: exports `renderText(diagnostics: Diagnostic[]): string` — formats into the human-readable stdout format shown in §7 (used by `check.ts` and `explain.ts`).
- `json.ts`: exports `renderJson(result: CheckResult): string` — serializes to the frozen `--json` schema from §10.
- `mermaid.ts`: exports `renderMermaid(graph: Graph, checkResult: CheckResult, opts: {noTimestamp: boolean}): string` — emits the `.mmd` flowchart per §9 (node ids, label, style classes, violation styling), with nodes/edges sorted lexicographically by path for determinism. Any shared label-escaping/id-computation logic used internally is a non-exported local helper in the same file, not a second export.
- `dot.ts`: exports `renderDot(graph: Graph, checkResult: CheckResult): string` — Graphviz DOT equivalent for `--format dot`.
- `html.ts`: exports `renderHtml(mermaidSrc: string, checkResult: CheckResult, opts: {noTimestamp: boolean}): string` — wraps the mermaid source in the self-contained CDN-loading page (legend + header line with file/edge/error counts + timestamp, omitted under `--no-timestamp`).
- `diff.ts`: exports `renderDiff(proposals: SuggestProposal[]): string` — renders the unified-diff-style `PREVIEW — not applied` blocks used by `suggest.ts` (`SuggestProposal` is a non-exported local type defined in `suggest.ts` and passed by shape, or added to `types.ts` if shared — implementer's choice, doesn't affect any module's export count either way).

### 10. `src/init.ts` (hub, in-degree 1 ← cli.ts)

- Exports exactly one function, satisfying R4: `run(repoRoot): void` — refuses to overwrite an existing `spokes.config.json` (exit 2 with a clear message), otherwise writes the default config object from §5 (pretty-printed JSON) and prints next-step instructions (`spokes check`, `spokes graph`).

### 11. `src/check.ts` (hub, in-degree 1 ← cli.ts; → types.ts, rules/r1..r4, render/text.ts, render/json.ts)

- Exports exactly one function, satisfying R4: `run(graph: Graph, config: SpokesConfig, opts: {json: boolean}): {result: CheckResult, exitCode: 0|1}`.
- Runs R1→R2→R3→R4 in order (R3 via `r3.analyzeCycles(graph, config).diagnostics`, the other three via their `check()` exports), splits diagnostics into `errors`/`warnings` by severity, computes `stats` (node/edge/hub/spoke/unmarked counts), prints via `render/text.ts` or `render/json.ts` depending on `opts.json`, returns the exit code per §7 (0 if no errors, 1 otherwise; config/usage failures are handled earlier in `cli.ts`/`config.ts` as exit 2).

### 12. `src/graph.ts` (hub, in-degree 1 ← cli.ts; → types.ts, render/mermaid.ts, render/dot.ts, render/html.ts)

- Exports exactly one function, satisfying R4: `run(graph: Graph, checkResult: CheckResult, opts: {format, noTimestamp, out}): void`.
- Writes `spokes-graph.mmd` and `spokes-graph.html` always; writes DOT only when `--format dot` is passed (per §9, DOT is an additional/optional output, not a replacement). Applies the >300-node directory-split behavior from §9, printing the split notice to stdout.

### 13. `src/suggest.ts` (hub, in-degree 1 ← cli.ts; → types.ts, rules/r3-acyclicity.ts, render/diff.ts)

- Exports exactly one function, satisfying R4: `run(graph: Graph, config: SpokesConfig): void`.
- For each cycle from `r3.analyzeCycles(graph, config).cycles`, computes the longest common directory of member paths, proposes `shared.hub.ts` there with `// @spokes hub` + TODO-stub re-exports (names only) of each member's exported symbols, computes the rewiring diff per member (redirecting its cycle-internal outgoing edge), renders via `render/diff.ts` with the `PREVIEW — not applied` label, and prints the verbatim honesty caveat from §8. `--write` is a recognized-but-rejected flag: prints "not implemented" and exits 2.

### 14. `src/explain.ts` (hub, in-degree 1 ← cli.ts; → types.ts, render/text.ts, rules/r1-spoke-outdegree.ts, rules/r2-hub-indegree.ts, rules/r3-acyclicity.ts, rules/r4-single-export.ts)

- Exports exactly one function, satisfying R4: `run(graph: Graph, config: SpokesConfig, targetPath: string): void` — prints one file's card: resolved role, incoming/outgoing edges with locations, export list, and per-rule pass/fail status covering **all four rules including R3** (a file that's part of a cycle must show as failing in `explain`, not just in `check`). Reuses `rules/r1..r4.ts`'s exported `check()` functions (r1/r2/r4) and `r3.analyzeCycles().cycles` directly (filtering R1/R2/R4 output to diagnostics whose `primary.file` is `targetPath`, and filtering `.cycles` to those containing `targetPath`) rather than re-implementing the degree/export/cycle logic inline — `explain.ts` is a hub with unconstrained out-degree, so there is no degree-rule reason to duplicate rule logic, and importing the real rules keeps `explain` and `check` from ever disagreeing about a file's status.

### 15. `src/cli.ts` (hub, in-degree 0 — the entry point; → init.ts, check.ts, graph.ts, suggest.ts, explain.ts, graph-builder.ts, core/config.ts, types.ts; external dep: `commander`)

- Exports a single `main(argv: string[]): Promise<number>` (returns the process exit code) — this satisfies R4 (single-export, applies to hub nodes too) the same way every sibling hub module exports exactly one `run`/`buildGraph` function. A thin `#!/usr/bin/env node` bootstrap at the bottom of the same file calls `main(process.argv)` and sets `process.exitCode`; that top-level call isn't itself an export, so it doesn't add to the export count.
- `main()` wires up `commander` with the 5 subcommands from §10.
- For `check`/`graph`/`suggest`/`explain`, loads config via `config.ts`, builds the graph exactly once via `graph-builder.ts`, then calls the relevant command module's `run(graph, ...)`. This single build-then-fan-out is the load-bearing detail that keeps `graph-builder.ts` at hub in-degree 1 while still serving four consumers.
- Maps internal panics (uncaught exceptions) to exit code 3 with a bug-report URL, per §7.

### 16. `fixtures/` (test-only, excluded from the linter's own `include`)

One directory per row in PRD §11 (`f01-clean-tree` … `f10-big-det`), each a minimal mini-repo with its own `spokes.config.json` (or reuse of defaults) and an `expected.json` matching the `check --json` schema with paths relativized. `tests/fixtures.test.ts` iterates the fixtures, runs the real CLI pipeline (`config → graph-builder → check`) against each, and asserts against `expected.json`. `f10-big-det` additionally asserts `graph --no-timestamp` run twice produces byte-identical `.mmd` output.

### 17. Meta dogfooding

No separate file — `tests/meta.test.ts` runs `spokes check` against `spokes`'s own `src/` (using the repo's real `spokes.config.json`, which must be created by running `spokes init` once during scaffolding and then hand-tuned so `roles` marks `src/*.ts` — i.e. `cli.ts`, `init.ts`, `check.ts`, `graph.ts`, `suggest.ts`, `explain.ts`, and `graph-builder.ts`, all top-level — as hubs, and everything under `src/core/`, `src/rules/`, `src/render/` as spokes) and asserts exit code 0. `graph-builder.ts`'s top-level placement (§7) is what makes this config classify it correctly. **`types.ts` is the one exception** to the `src/*.ts → hub` glob — it carries its own `// @spokes spoke` file pragma (§2), which wins over the config glob per §4, so it stays a spoke despite living at the same top level.

## Technical Considerations

- **No auto-generated abstractions beyond what §13's suggested shape calls for** — the file list above is exactly the PRD's suggested shape (`cli.ts` → `check/graph/suggest/explain.ts` → `parser/resolver/rules/render`) plus the minimum extra spokes (`types.ts`, `config.ts`, `roles.ts`, `graph-builder.ts`) needed to make it acyclic and degree-legal.
- **Determinism**: all render modules sort nodes/edges lexicographically before emitting; no reliance on `Map`/glob iteration order anywhere output touches disk.
- **No banned deps**: JSON Schema validation and glob-role-matching are hand-rolled (minimal, scoped to the exact shapes in §5) specifically because `ajv`/`micromatch`/`minimatch` are not in the allowed dep list (`typescript`, `fast-glob`, `commander` only).
- **Edge Cases**: self-imports (a file importing itself) — treated as a normal edge for degree-counting purposes but excluded from cycle length reporting if trivially a 1-node cycle (still reported as a valid `S003`, cycle length 1). Barrel files (`index.ts` re-exporting many things) will naturally trip R1 if marked spoke — this is intended, not a bug to special-case. Multiple import statements from the same file to the same target on different lines — deduplicated per §6 into one edge with multiple locations, confirmed in `f01`/fixtures via files with repeated imports where relevant.

## Type Definitions

Centralized in `src/types.ts` per Implementation Detail §2: `Role`, `Loc`, `Node`, `Edge`, `Graph`, `Diagnostic`, `SpokesConfig`, `CheckResult`, `Cycle`. No duplicate/ad-hoc type definitions elsewhere — every other module imports from here, which is also what keeps `types.ts` a valid zero-out-degree leaf.

## Performance & Cost Impact

Target ≤2s for 1,000 files. Key decisions supporting this: `tsconfig.json`/compiler options parsed once per run (not per file) in `resolver.ts`; `ts.createSourceFile` used directly instead of a full `ts.Program`/type-checker (avoids full semantic analysis, which is unnecessary — only syntactic import/export extraction is needed); file contents read once and reused for both pragma-scanning and AST parsing. No network calls at runtime (only the generated HTML's CDN reference, never fetched by the tool itself).

## Backward Compatibility

N/A — greenfield project, no prior version to migrate from.

## Test Impact

- All new logic; no existing tests to break.
- `tests/rules/*.test.ts`: one suite per rule (R1–R4), snapshot-testing exact diagnostic message text against the §7 templates (verbatim match requirement from §13).
- `tests/fixtures.test.ts`: drives f01–f10 through the real pipeline, asserting against each fixture's `expected.json`.
- `tests/meta.test.ts`: dogfooding — `spokes check` on the tool's own `src/` must exit 0.
- `tests/render/determinism.test.ts` (covers f10): two consecutive `graph --no-timestamp` runs on an unchanged fixture must produce byte-identical `.mmd`/`.html` output.
- No E2E/browser test needed for the generated HTML beyond string/snapshot assertions — visually opening it is a manual sanity check, not an automated one, since Mermaid rendering itself is delegated to the CDN script at view time.

## For New Commands

Every new `spokes` CLI subcommand must be added as a hub module owned solely by `cli.ts` (in-degree 1), receiving any shared `Graph`/`SpokesConfig` state as a function argument from `cli.ts` rather than importing a shared builder — this is what keeps `graph-builder.ts` at hub in-degree 1 as the command surface grows. New rule modules (`R5`+) follow the `rules/r*.ts` spoke pattern: single `types.ts` import, pure `(graph, config) => Diagnostic[]` function, message template committed to §7-style docs and snapshot-tested verbatim.
